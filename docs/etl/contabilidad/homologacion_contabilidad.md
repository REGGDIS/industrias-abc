# Claves candidatas de homologación — Contabilidad

**Proyecto:** Plataforma de Business Intelligence — Industrias ABC · Equipo BInnova
**Dominio:** Contabilidad (PostgreSQL) · **Responsable:** Raymond Civil
**Etapa:** ETL Contabilidad 0.1 — preparación de homologación · **Versión:** 0.1

## Qué es la homologación (y qué NO afirma este documento)

**Homologar** es reconocer que un mismo objeto del mundo real (un área, un centro de
costo) aparece en varias fuentes y hacerlos corresponder para integrarlos más adelante
en el Data Warehouse. Este documento **solo identifica claves candidatas** del dominio
Contabilidad; **no define equivalencias definitivas**. La correspondencia real se
**definirá y cerrará en el ETL Core**, con evidencia y con todas las fuentes disponibles.

> **Advertencia central:** la **igualdad textual de un código entre dos fuentes NO
> constituye por sí sola una equivalencia definitiva.** Dos fuentes pueden usar el mismo
> texto para objetos distintos, o textos distintos para el mismo objeto.

## Por qué NO se usan los IDs locales

Los identificadores `area_id`, `centro_costo_id`, `cuenta_id` y `movimiento_id` se
generan con `BIGINT GENERATED BY DEFAULT AS IDENTITY`: **cada base los numera por su
cuenta**. Un `area_id = 4` en Contabilidad **no** equivale a un `area_id = 4` en RRHH o
Compras. Por eso los IDs locales se **conservan solo como trazabilidad** (rastrear el
registro hasta su fuente) y **nunca** se usan como equivalencia entre sistemas.

## Matriz de claves candidatas

| Entidad / campo | ID local (trazabilidad) | Clave candidata | ¿Con qué fuente se relacionaría? | Condición para un match válido | Riesgo de falso match / limitación |
|---|---|---|---|---|---|
| Área | `area_id` | `codigo_area` | RRHH, Compras, Universo Master | Mismo esquema de códigos de área, confirmado contra el Master | El Master indica que las fuentes pueden usar códigos/nombres distintos; igualdad textual no garantiza misma área |
| Centro de costo | `centro_costo_id` | `codigo` | Compras, Universo Master (centros comunes) | Catálogo de centros de costo acordado/validado entre fuentes | Un mismo código podría reutilizarse con distinto significado entre sistemas |
| Cuenta contable | `cuenta_id` | `codigo_cuenta` | **Ninguna otra fuente** (plan de cuentas propio de Contabilidad) | No aplica cruce externo en esta etapa | Es clave de negocio **interna**; ninguna otra fuente tiene plan de cuentas — no homologar con nada externo por ahora |

## Campos de estandarización de dominio (NO identifican entidades)

| Campo | Uso candidato | Por qué NO es clave de identidad |
|---|---|---|
| `moneda` | Estandarización de un **dominio común** de monedas (p. ej. CLP, USD, EUR / ISO 4217) | Identifica una moneda, no una entidad de negocio; sirve para unificar el catálogo de monedas, no para emparejar registros entre fuentes |
| `documento_tipo` | Candidato a **catálogo común** de tipos de documento, si el proyecto lo define posteriormente | Sus valores pueden no calzar entre fuentes; es una referencia categórica, no una identidad |

## Cómo funcionaría técnicamente (referencia, no se implementa aún)

La homologación se resolvería en el ETL con un **cruce (`JOIN`)** sobre la clave
candidata **ya normalizada** en staging (por eso se limpia con `TRIM`/`UPPER`). El
criterio real (igualdad de código, tabla de equivalencias, o reglas adicionales) lo
**define el ETL Core**; el ejemplo es solo ilustrativo:

```sql
-- Ejemplo ILUSTRATIVO (no se implementa en esta etapa). Criterio real: ETL Core.
SELECT c.codigo_area,
       c.area_id AS area_id_contabilidad,   -- ID local (trazabilidad)
       r.area_id AS area_id_rrhh              -- ID local del otro sistema
FROM   stg_contabilidad_areas_limpio c
JOIN   stg_rrhh_areas_limpio          r
       ON UPPER(TRIM(c.codigo_area)) = UPPER(TRIM(r.codigo_area));  -- regla candidata, a confirmar
```

## Límites de esta matriz

Estas son **claves candidatas para el trabajo ETL**, no claves del Data Warehouse. No se
crean `DIM_*`, `FACT_CONTABILIDAD`, claves subrogadas ni mappings definitivos. Cualquier
decisión de equivalencia entre Contabilidad y otra fuente (áreas, centros, moneda o tipo
de documento) debe **elevarse al ETL Core antes de codificarse**, con evidencia — nunca
asumida por igualdad textual.
